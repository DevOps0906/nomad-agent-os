# plan-docs — 기획을 싸게, 빠짐없이

## 원칙
1. **목차 먼저, 본문은 나중**: 팀장(Opus)이 목차·핵심 결정만 정한다(짧은 출력). 본문은 planner(Sonnet)가 섹션 단위로 채운다.
2. **섹션 병렬**: 서로 독립된 섹션은 planner 여러 명에게 동시에 맡긴다. 각 지시에는 그 섹션의 입력 경로만 준다.
3. **한 사실은 한 곳**: 같은 내용을 두 문서에 쓰지 않는다. `01_PRD.md#3`처럼 링크한다.
4. **표 > 목록 > 문장**: 같은 정보면 표가 가장 짧다. 문단 서술은 "왜"에만 쓴다.
5. **길이 상한**: 아래 표를 넘으면 쪼갠다. 길이가 곧 다음 작업의 읽기 비용이다.
6. **린 검증 게이트**: 새 제품·기능은 `00_LEAN.md`가 통과해야 PRD로 간다(검증 전 정식 개발 금지).

## 절차
0. 문서가 없으면 `~/.claude/nomad/bin/plan-scaffold docs --name "<제품명>"`으로 뼈대를 만든다(모델 토큰 0, 기존 파일 보존).
1. 팀장: 기존 문서를 `scout`로 훑게 해 "이미 있는 것" 목록을 받는다(문서 통독 금지). 문서가 갱신됐으면 `delta`로 바뀐 줄만 본다.
2. 팀장: 목차 + 결정 목록 + 미결 질문을 쓴다. 미결이 제품 방향이면 사용자에게 묻는다.
3. planner: 섹션별 병렬 작성. 다이어그램이 필요하면 요청만 남긴다 → diagrammer(종류는 `diagram` 스킬 8종 표). UX·IA·흐름은 `codex-designer`와 공동 작성·교차 검토(1회, 심각 충돌 시 1회 추가, 이후 팀장 결정; Codex 불가 시 designer).
4. reviewer(mode=doc): 모순·중복·근거 없는 수치·누락 점검. PRD `8. 보안·공급망`이 비었거나 노출 면에 위협 메모가 없으면 🔴. 위험 기능이면 challenger 추가.
5. 작업 분해: 작업 하나 = 한 세션에서 끝나는 크기. 각 작업에 "근거: 문서#장"을 적어 구현 때 그 장만 읽게 한다. `보안 영향`이 있으면 위험도 높음. PRD 보안 레벨이 L1·L2면 `/secure setup` 작업을 W1에 넣는다.

## 수익·사업 관점 (기획마다 1줄씩)
수익 모델 · 가장 싼 검증 방법(랜딩·크몽·사전예약) · 자동화 가능성 · 정부지원사업 연결 가능성.
