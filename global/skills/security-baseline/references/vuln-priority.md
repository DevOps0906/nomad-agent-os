# 취약점 우선순위 — CVSS 점수만 보지 않는다

## 1. 왜
CVSS는 취약점 하나를 따로 평가한다. 실제 공격은 **중간·낮은 등급 여러 개를 이어 붙여**(체이닝) 심각한 침해로 만든다.
그래서 "점수가 낮으니 나중에"로 쌓아 둔 취약점이 체인의 재료가 된다.

## 2. 판단 순서 (위에서부터 해당하면 먼저)
| 순위 | 신호 | 뜻 |
|---|---|---|
| 1 | **KEV 등재** (CISA Known Exploited Vulnerabilities) | 실제로 악용되고 있음 |
| 2 | **인터넷 노출 + 도달 가능** | 공개 API·웹훅·관리자·업로드 경로에서 그 코드가 실행됨 |
| 3 | **체인의 중간 고리** | 점수는 낮아도 다른 약점과 이어져 권한 상승·데이터 접근으로 가는 길을 엶 |
| 4 | **EPSS 높음** (악용 가능성 예측, 예: 0.1 이상) | 곧 악용될 가능성 |
| 5 | **피해 범위 큼** | 뚫리면 service_role·결제·전체 조직 데이터·에이전트 키까지 닿음 |
| 6 | CVSS 점수 | 위 신호가 없을 때 정렬용 |

## 3. 처리 기한 (기본값, PRD 8절에서 조정 가능)
| 분류 | 기한 |
|---|---|
| 순위 1, 또는 순위 2+3 | 즉시 (작업 중단하고 처리) |
| 순위 2 또는 3 또는 4 | 7일 |
| 그 밖의 high/critical | 30일 |
| 그 밖의 low/medium | 다음 의존성 정리 때 — **무기한 보류 금지** |

## 4. 실제로 영향이 없을 때 — VEX식 기록
"우리 제품에서 악용 가능한가"를 판단해 남긴다. `security/vex.md`(또는 L3에서 OpenVEX/CycloneDX VEX):
| 취약점 | 컴포넌트 | 상태 | 근거 | 날짜 |
|---|---|---|---|---|
| CVE-… | pkg@ver | not_affected / affected / fixed / under_investigation | 예: 해당 함수 미호출(`codemap`·Grep 근거), 서버 빌드에 미포함 | YYYY-MM-DD |

`not_affected`는 근거가 있을 때만. "도달 불가"는 다른 약점이 길을 열면 무너지므로, 노출 면이 바뀌면 다시 본다.

## 5. 도구
`secscan vuln` (OSV 기반, 없으면 npm/pnpm audit · pip-audit) → `secscan vuln --kev`로 KEV 표시(네트워크 필요, 실패해도 진행).
